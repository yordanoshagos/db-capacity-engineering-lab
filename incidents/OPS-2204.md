# OPS-2204 — Nightly export crashes the service; on-call paged for repeated restarts

| Field        | Value                                    |
|--------------|------------------------------------------|
| **Priority** | P2 — High                                |
| **Status**   | Open                                     |
| **Reported by** | Data / ETL team + on-call             |
| **Component** | `capacity-api`                          |
| **Affected endpoint** | `GET /api/patients/export`      |

## Report (in the reporter's words)

> "Our nightly analytics job pulls the **full patient export** from the API.
> Ever since the patient table grew, the service **restarts over and over**
> during that window and on-call gets paged. The memory graph shoots straight up
> right before each restart. Regular reads during the day are totally fine —
> it's specifically the big export that takes the whole service down with it, and
> it takes down *other* users' requests too while it's thrashing."

## What we know

- Correlated with the growth of the patient table (~100,000 rows and climbing).
- Memory climbs sharply just before each restart.
- Small/normal reads are unaffected.
- The service runs in a **256MB** container in production; locally we cap it
  even tighter (**160MB**) so the ceiling is reachable within a 2-minute run.
- The failure is not isolated to the export caller — it degrades the whole
  instance.

> ⚠️ **This is a field hypothesis, not a verdict.** The suspected cause and
> symptoms above come from whoever filed the ticket — they may be incomplete or
> simply wrong. Your job is to find what is *actually* happening. Disproving the
> reported cause with evidence is a full-marks answer, not a failure.

## Your task

1. Baseline the system (`load-tests/00-baseline.js`).
2. Reproduce the nightly job: `k6 run load-tests/reproduce-OPS-2204.js`.
3. Watch memory and restarts (`docker stats`, `docker compose logs -f
   capacity-api`, and the `nodejs_heap_size_used_bytes` metric). Work out how
   much memory one export needs, how that scales with concurrent callers, and
   why it exceeds the budget.
4. Propose and apply a fix that keeps memory bounded, then re-run and compare.
5. Document everything in `LAB_JOURNAL.md` (Investigation OPS-2204).

_Hint on where to look, not what you'll find: think about how much of the result
set has to exist in the application's memory at one time, and whether it has to._
